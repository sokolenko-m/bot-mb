Источник правды по поведению: `PRODUCT_SPEC.md`. Статус: реализовано 05.11.2026. Репозиторий публичный: сюда не пишем имена, Telegram ID и токены.

## Хранение: две базы в Notion, страница «Графік ресурсів»

Render не хранит файлы между деплоями, поэтому только Notion. Копии `backup.js` покроют базы автоматически, если интеграция их видит.

**«Плани місяця»**: одна строка на версию плана.

| Поле | Тип | Смысл |
|---|---|---|
| Назва | title | `2026-12 · Конструктор · v2` |
| Місяць | rich_text | `YYYY-MM` |
| Конструктор | people | |
| Версія | number | 1, 2, … |
| Стан | select | `Записується`, `Активний`, `Замінений` |
| Зафіксував | rich_text | Имя из Telegram и Telegram ID |
| Джерело | select | `Кнопка`, `Резервна копія` |
| Примітка | rich_text | Пометка, например о восстановлении из копии |
| Задач / Годин | number | Рабочие задачи без отсутствий |

Дата фиксации берётся из `created_time`.

**«Задачі плану»**: одна строка на задачу версии.

| Поле | Тип |
|---|---|
| Назва на момент фіксації | title |
| План | relation → «Плани місяця» |
| № задачі | rich_text (`KV-420`, может быть пустым для ноября) |
| ID сторінки | rich_text (id задачи в Notion) |
| Об'єкт, Тип задачі | rich_text |
| Порядок, План год | number |
| Початок, Кінець, Додано | date |
| Відсутність | checkbox |

Связи с базой задач relation не делаем намеренно: снимок не должен зависеть от судьбы задачи, а изменение схемы «Задачи» вызвало бы предупреждение планировщика. Схема «Задачи» не меняется.

## Запись версии

1. Прочитать задачи конструктора за месяц той же функцией, что обычный отчёт.
2. Сравнить с активной версией по id страницы. Без изменений → ответ `unchanged`, запись не выполняется.
3. Создать шапку со `Стан = Записується`.
4. Создать строки задач с паузами под лимит Notion (около 3 запросов в секунду).
5. Сверить число строк с `Задач`.
6. Прежней активной поставить `Замінений`, новой `Активний`.
7. При сбое на шагах 3–5 активная версия не меняется. Шапка `Записується` не читается никогда.

Двойное нажатие: блокировка в памяти процесса по ключу месяц+конструктор, плюс проверка шапки `Записується` моложе 5 минут → ответ 409. На Render один процесс, этого достаточно.

## API

Все маршруты под `requireTelegramAuth`.

| Маршрут | Доступ | Ответ |
|---|---|---|
| `GET /api/plans?month=` | Отчёты | Список конструкторов с активной версией |
| `GET /api/plans/preview?month=&constructorId=` | Отчёты | Задачи и отличия от активной версии |
| `GET /api/me` | Отчёты | Право фиксации, текущий и следующий месяц |
| `POST /api/plans/fix` | **Только фиксирующие** | Новая версия, PDF в чат |
| `POST /api/plans/pdf` | Отчёты | PDF сохранённого плана в чат |
| `GET /api/plans/versions?month=&constructorId=` | Отчёты | История версий |
| `POST /api/reconcile` | Отчёты | Строки и итоги |
| `POST /api/reconcile/export` | Отчёты | PDF или Excel в чат |

Право фиксации: env `PLAN_EDITOR_IDS` (Telegram ID через запятую), проверка на сервере. Не Notion, потому что появление Telegram ID руководителя в «Участники_1» включает ему сообщения бота конструкторов, а этого пока не хотят. Месяц валидируется: формат `YYYY-MM`, только текущий и следующий для фиксации, текущий день берётся по Киеву.

## Алгоритм сверки (`reconcile.js`)

Вход: активная версия плана, текущие задачи конструктора, текущие состояния плановых задач по id, `monthEnd`, `today`.

1. **Плановая строка** на каждую задачу плана: часы и номер из снимка, название текущее, при отличии добавляется `(у плані: …)`.
2. **Состояние:** страница не найдена или в корзине → `Видалена`; конструктор сменился → `Передана: …`.
3. **Дата закрытия:** «Факт. завершення», иначе при 100 % плановый «Конец» (правило бота).
4. **Выполнена:** дата закрытия ≤ `monthEnd` и ≤ `today`. Дата > `today` → пометка о будущей дате. `monthEnd` < дата ≤ `today` → `Закрита ДД.ММ`.
5. **Продолжения:** задача того же конструктора, не из плана, с той же базовой названием (`baseTitle`) и суффиксом «(продовження)» присоединяется к плановой; выполнена, когда закрыты все части; факт суммируется. Несколько продолжений с одной базой присоединяются к плановой с этой базой; если плановых с такой базой несколько, к ближайшей по дате.
6. **Новые:** задачи конструктора вне плана, не отсутствие, не продолжения плановых, у которых «Начало» или дата закрытия в месяце.
7. **Итоги:** считаются только из строк, чтобы таблица и итоги не могли разойтись. План: сумма часов снимка без отсутствий. Выполнено: факт, иначе план; фактические часы при закрытии раньше «Начало» считаются пустыми (фантомы, см. A5 в `MAXIBUD.md`).

Известное ограничение: продолжение связывается по названию. Если конструктор переименует только продолжение, оно будет показано как новая задача, а плановая останется невыполненной. Это видно глазами в таблице.

## Импорт ноября

Разовый скрипт с ноутбука, не код сервера. Читает копию `2026-10-30_1700`, отбирает по тем же правилам задачи с «Начало» в ноябре по каждому конструктору, номер KV подставляет из текущего Notion по id страницы. Записывает версию 1 с `Джерело = Резервна копія`. В копии одна база лежит в нескольких файлах, поэтому строки объединяются по id страницы. Сначала режим просмотра без записи: число задач и часов по конструкторам.

## Тесты

`node --test`, сеть подменена, как в `reports.test.js`.

- `reconcile`: каждый случай из раздела «Как проверим» `PRODUCT_SPEC.md`, границы месяца по Киеву.
- `plans`: версии, `unchanged`, сбой посередине, блокировка, контрольные суммы.
- API: отказ без права фиксации, неверный месяц, прошедший месяц.
- Экспорт: три строки равны подсчёту по строкам.
- Регрессия: прежние тесты обычного отчёта.

## Порядок работ

1. `reconcile.js` и тесты.
2. Базы Notion (сначала тестовые) и `plans.js`.
3. API и раздел Mini App.
4. Экспорт сверки.
5. Импорт ноября, просмотр без записи, затем запись.
6. Проверка на тестовых базах с настоящими задачами, проверка в браузере, security review прав и входных данных.
7. Настройка `PLAN_EDITOR_IDS` на Render, рабочие базы, деплой.

## Что нужно проверить при реализации

- Токен на Render принадлежит той же интеграции и имеет право записи. В коде отчётов сейчас только чтение.
- Доступ интеграции к новым базам, чтобы их увидел `backup.js`.
- Базы видны участникам Notion, строки можно изменить вручную. Правки видны в истории Notion. Закрыть доступ можно настройками страницы, это решение за владельцем.
